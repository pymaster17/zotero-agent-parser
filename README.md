# Zotero Agent Parser

一个 Zotero 插件（Zotero 7 及以上），在添加新条目时自动把 PDF 交给 MinerU 解析成 Markdown，，方便 agent 直接读取。解析产物放在 PDF 所在的附件目录里，通过 WebDAV 同步到其他电脑。

## 版本与安装

插件分两个版本，按需选择：

| 版本 | 文件 | 内容 |
|---|---|---|
| 轻量版 Agent Parser Lite | `agent-parser-lite-<版本>.xpi` | 只用云端（mineru.net），不含本地 MinerU 的安装和服务管理 |
| 完整版 Agent Parser | `agent-parser-<版本>.xpi` | 云端 + 本地 MinerU |

两个版本的插件本体都只有几十 KB。完整版只有在设置页点「安装」后，才会下载 Python 环境和模型（约 4.8 GB）。两个版本共用同一个插件 ID 和设置，装其中一个会替换另一个，Token 等设置会保留。

```sh
./build.sh          # 同时生成 build/agent-parser-<版本>.xpi 和 build/agent-parser-lite-<版本>.xpi
./build.sh lite     # 只打包轻量版
./build.sh full     # 只打包完整版
```

在 Zotero 中打开「工具 → 插件」，点右上角齿轮选「从文件安装插件…」，选择对应的 `.xpi`。

发布新版本：

1. 修改 `manifest.json` 中的 `version`。
2. 运行 `./build.sh && ./update-manifests.sh`。
3. 提交并推送 `updates.json` 和 `updates-lite.json`。
4. 创建 `v<版本>` Release，上传 `build/` 中的两个 `.xpi`。清单里记录了文件哈希，所以上传的必须正是这一步生成的文件。

## 解析方式

在「设置 → Agent Parser」中选择默认解析方式（轻量版只有云端）：

| 方式 | 说明 | 需要配置 |
|---|---|---|
| 云端（mineru.net v4 API） | 速度快，不占本机资源，消耗解析额度 | 在 mineru.net API 管理页申请的 Token |
| 本地（在本机运行 MinerU） | 不依赖网络和额度，速度取决于本机硬件 | 点「安装」构建环境并下载模型 |

右键菜单里还有「用云端服务重新解析 PDF」和「用本地 MinerU 重新解析 PDF」，可以临时改用另一种方式。

**本地模式下的批量请求**：整库解析、多选条目这类批量请求，默认改走云端批处理，前提是填了 Token。原因是本地逐篇处理太慢：M4 上 standard 档一篇论文约 1 分钟。可以在设置中取消「大批量请求使用云端批处理接口」。

### 本地 MinerU

勾选「由 Agent Parser 安装并运行 MinerU」（默认勾选）后，点「安装」，插件会依次完成：

1. 创建 Python 3.12 虚拟环境，默认位置是 `~/.zotero-agent-parser/mineru-env`。优先用 [uv](https://docs.astral.sh/uv/) 创建；没有 uv 时，退回到系统的 Python 3.11–3.14 和 `venv`。
2. 安装 `mineru>=4.1,<5`。在 Apple Silicon 上还会额外安装 MLX 推理引擎（`mineru-vl-utils[mlx]`），实测比 MinerU 在 Mac 上默认选的 llama.cpp 快约 1.5 倍。
3. 按所选档位下载模型，存放在 MinerU 的默认位置 `~/.mineru/models`，可以和其他 MinerU 安装共用。

全部下载约 4.8 GB，其中 Python 环境约 1.7 GB、模型约 3 GB。basic 档不需要 VLM，约 2.6 GB。安装过程和日志在设置页中实时显示，可以随时取消；之后点「更新 / 修复」可以升级 MinerU 或补齐缺失的模型。模型下载慢时，可以把「模型来源」改为 ModelScope。

解析时插件会自动启动 `mineru-kit api-server`，只监听 127.0.0.1，并带上这些设置：

- 一次只处理一个任务。MLX 推理本身是串行的，实测两篇同时跑并不会更快。
- 关闭图片分析。这项功能会把图转成 mermaid 流程图，对 agent 用处不大，而且在复杂框图上可能陷入重复生成。

服务空闲 15 分钟后自动停止，释放约 3 GB 内存；时长可在设置中调整，设为 0 表示不停止。Zotero 退出时，服务也会一起停止。

档位（M4 16 GB、MLX 实测，3 篇 arXiv 论文共 56 页）：

| 档位 | 速度 | 说明 |
|---|---|---|
| basic | 最快 | 只用小模型，公式和复杂版面质量最低 |
| standard（默认） | 约 3.5 秒/页 | 小模型做版面分析，VLM 识别文本、公式和表格 |
| advanced | 约 13 秒/页 | 版面也交给 VLM，表格多的文档质量更好 |

如果想用自己运行的 MinerU 服务（本机或局域网内的其他电脑），取消「由 Agent Parser 安装并运行 MinerU」，然后填写服务地址和 API Key。服务需为 `mineru-kit api-server`，MinerU 版本 ≥ 4。

### 云端

**URL 直传**：从白名单域名保存的 PDF，插件会把附件记录的下载地址直接交给 MinerU，由服务端自己下载，省去上传时间。提交前插件会先请求一次该地址，确认返回的是 PDF 且大小与本地文件一致；不满足条件，或 MinerU 下载/解析失败时，自动改为上传本地文件。`full.md` 的 YAML 中 `parser_input` 记录了实际使用的方式。

默认白名单（可在设置中修改，子域名也算在内）：`arxiv.org`、`aclanthology.org`、`isca-archive.org`（Interspeech 等）、`jmlr.org`、`openaccess.thecvf.com`、`proceedings.iclr.cc`、`proceedings.mlr.press`（ICML 等）、`proceedings.neurips.cc`。这些站点不需要登录就能直接下载 PDF，并且会返回文件大小。需要登录或机构权限的站点（IEEE Xplore、ACM DL、ScienceDirect）、带反爬虫拦截的站点（OpenReview、MDPI），以及不返回文件大小的站点（AAAI、HAL），加入白名单也用不上。

## 状态与提示

日常使用不需要操作：新加入的 PDF 会自动排队解析。只有首次设置和解析出错时才需要处理。

- **工具栏状态灯**（同步按钮左侧）只用来显示状态：
  - 绿色 ✓：没有解析任务
  - 黄色（转动）：正在解析，角标为进行中和排队的数量
  - 红色 !：出现异常，包括解析失败（角标为失败数量）和需要完成设置（未填写 Token，或本地 MinerU 尚未安装）。需要设置时，新的 PDF 会留在队列里，设置完成后自动开始

  点击状态灯会弹出详情：云端和本地各自的进行中、排队、稍后重试、等待设置数量，每个正在解析的文件及其阶段（上传、在服务端排队、解析、保存），以及失败的文件和原因。点击文件可以定位到对应条目。
- **条目列表的「Agent Parser」列**：安装后自动显示在列表最右侧（之后可以在列标题上右键隐藏或再次显示），每个条目显示 ✓（已解析）、!（失败）、转圈（解析中）、时钟（排队）、⚠（等待设置）或虚线圆圈（未解析）。点击列标题可按状态排序，失败的排在最前。
- **条目面板的「Agent 解析」栏**：显示所选条目每个 PDF 的状态、进度或错误信息，并提供「重试」「改用云端 / 本地重试」「打开 Markdown」「在文件夹中显示」「重新解析」等按钮。
- **通知**：解析完成（✅）和失败（❌）时右下角弹出提示，可在设置中关闭。
- **设置页顶部的「状态」栏**：显示设置是否完成、队列和失败数量，可一键跳到需要填写的位置。首次安装时如果还没有设置，会自动打开设置页。

失败记录会保存下来，重启 Zotero 后仍然可见，直到重试成功或手动清除。

**超出服务限制**是一类单独的失败：云端只接受 200 MB / 200 页以内的文件。插件提交前会先检查大小和页数，超出的直接标为「超出服务限制」，不再上传；服务端返回的同类错误也按此处理。因为重试一定会再次失败，设置页的「重试失败项」会跳过它们，条目面板里提供「用本地 MinerU 解析」（完整版）。本地模式下，被分流到云端批处理的大批量请求遇到这种文件时，会自动退回本地解析，不记为失败。

## 触发方式

- **自动**：通过浏览器 Connector、拖入文件、「查找可用 PDF」等方式新增 PDF 附件时，插件会等文件下载完成，再加入解析队列。
- **手动**：在条目上右键，可选择「解析 PDF 为 Agent 可读格式」「强制重新解析 PDF」「显示解析结果」。
- **批量**：「工具 → 解析当前库中所有未解析的 PDF…」，或在右键菜单中一次选中多篇。首次安装后初始化整个库就用这个入口。

使用云端时，批量请求会按每批最多 50 篇提交：白名单域名的 PDF 合并成一个 URL 批次，其余合并成一个上传批次。文件逐个上传，服务端同时在解析已上传的文件，每篇解析完就立即保存。URL 方式失败的文件会自动改为上传重试。最多同时运行 4 个批次，也就是最多 200 篇同时交给服务端排队和解析；期间新添加的条目按单篇单独处理（默认最多同时 4 篇，可在设置中调整），不需要排在批次后面。每个批次结束时显示一条汇总通知，不会逐篇弹窗。

云端的排队和超时：

- 文件提交后，服务端可能先让它排队（状态为 `pending`）。每个账号每天有 1000 页最高优先级额度，超出部分优先级降低，排队时间会明显变长。
- 设置中的「解析超时」从服务端开始处理这篇文件时算起，排队时间不计入。文件在服务端排队超过 24 小时仍未开始，才判定为失败。
- 服务端拒收新任务时（提交队列已满或当日任务数达到上限），文件会放回插件的队列，15 分钟后再提交，不算失败。
- 文件交给服务端后，插件会把 MinerU 的任务编号存进队列。Zotero 重启或插件更新后，会先接着查询原来的任务，不会重新提交、重复消耗额度。以下情况才会重新提交：PDF 已经改变、解析设置（模型、OCR、公式、表格、语言）改了、提交已超过 3 天、服务端已经没有这个任务或结果，或者上次的上传没有完成。
- **上传加速**：MinerU 的文件存储（阿里云 OSS）在上海。从中国大陆以外上传时，数据要经过拥堵的国际出口，实测只有几 KB/s 到几十 KB/s，还容易断线。插件可以改走 OSS 的传输加速节点（`oss-accelerate.aliyuncs.com`），在海外就近进入阿里云网络，实测快一百倍以上。设置中的「上传加速」有三档：
  - 「自动」（默认）：每次启动后，先请求一次 OSS 直连地址，响应超过 300 ms 才使用加速；
  - 「始终」：总是先尝试加速；
  - 「关闭」：始终直连。

  加速上传失败时，会立即改用原地址上传。如果加速节点直接拒绝（例如存储桶关闭了加速），「自动」模式在本次运行期间不再尝试。这个用法依赖 MinerU 当前的 V1 预签名地址和存储桶的加速设置，并非 MinerU 正式支持的接口。
- 上传文件时连接中断，会在 30 秒、2 分钟、5 分钟后各重试一次；查询解析进度时遇到断网、超时或服务端 5xx 错误，会在下一轮继续查询，不会让任务失败。

**重复生成的回退**：解析结果偶尔会卡在同一段内容上反复输出，例如行内公式里重复几十次 `\mathbf { }`，或表格单元格里重复同一个词。插件检测到这种情况（同一段 8–400 字符的内容连续重复 5 次以上，合计超过 400 字符）后，会先保存这次的结果，再依次尝试：

1. **开启 OCR，用 vlm 重新解析。** 云端的 vlm 实际运行的是 MinerU 的 hybrid 后端：不开 OCR 时，正文取自 PDF 的文字层，行内公式交给一个小的公式识别模型，大部分重复就出在这里。pipeline 也用同一个公式模型，所以换成 pipeline 解决不了。开启 OCR 后，整行文字连同公式都由 VLM 识别。用同样的方式重新解析没有用，因为服务端对同一个文件会给出同样的结果。
2. **仍然重复时，改用 pipeline 模型。** pipeline 用独立的版面、OCR 和表格模型，可以处理 VLM 自身陷入的重复。
3. **还是重复时，保留原来的结果。**

只有结果不再重复，才会替换原结果。这时 YAML 中会记录 `parser_model`、`parser_ocr` 和 `parser_fallback_reason`。如果设置里已经开启了强制 OCR，会跳过第 1 步。

插件会把 PDF 的 SHA-256 写在 `full.md` 开头的 YAML 里。PDF 没有变化时，重复触发会直接跳过。队列保存在偏好设置中，Zotero 重启后会继续处理。

## 产物结构

```
<Zotero 数据目录>/storage/<附件键>/
├── 论文.pdf
└── parsed/                  # 文件夹名可在设置中修改
    ├── full.md              # Markdown 正文
    └── images/              # full.md 引用的插图（用相对路径引用）
```

`full.md` 开头是一段 YAML，记录标题、作者、年份、DOI、标签、`zotero://` 链接、源 PDF 的 SHA-256、所用模型（`parser_model`，开启 OCR 时还有 `parser_ocr`）和解析时间；正文中公式为 LaTeX，表格为 HTML。MinerU 会给每个公式和表格另存一张截图，但正文已经有对应的文本，所以 `images/` 中只保留 `full.md` 实际引用的图片，其余截图会被删除。解析服务返回的其他文件（JSON 中间结果、PDF 副本等）也会被丢弃。

## 同步说明（重要）

- **WebDAV**：Zotero 的 WebDAV 文件同步会把整个附件目录打成 ZIP 上传，`parsed/` 也包含在内。但 Zotero 只根据主文件（PDF）的修改时间判断是否需要同步，所以解析完成后插件会做两件事：把附件标记为待上传，并更新 PDF 的修改时间。这样其他电脑即使已经有这个 PDF，也会重新下载带解析产物的 ZIP。这一行为可以在设置中关闭（「解析完成后标记附件待上传」）。
- **Zotero 自带存储（ZFS）**：PDF 是作为单个文件上传的，不会附带 `parsed/`，因此产物**不会**通过 ZFS 同步。
- 「跳过从同步下载的条目」默认开启：从同步收到的新条目不会在本机重复解析，由添加它的那台电脑负责解析并上传。
- 链接文件（linked file）默认不解析。开启后，产物写在 PDF 旁边的 `<文件名>.parsed/` 文件夹中，不经过 Zotero 同步。

## 注意

- 本地服务产出的 `markdown.md` 和云端的 `full.md` 会统一整理成 `full.md`；YAML 中的 `parser` 字段为 `mineru-local` 或 `mineru-cloud-v4`。
- API Token 和 Key 以明文保存在 Zotero 配置目录的 `prefs.js` 中。
- 云端 v4 API 对单个文件的限制是 200 MB / 200 页。超过 200 页的 PDF 在提交前会被直接跳过，不会解析；超过 200 MB 时任务会失败并弹出通知。需要解析长文档时，可以先拆分 PDF，或改用本地 MinerU。
- 上传给服务端的文件名统一为 `<附件键>.pdf`，以避开非 ASCII 文件名带来的问题；原文件名会记录在 `full.md` 开头的 YAML 中。
- 自动更新：完整版读取仓库根目录的 `updates.json`，轻量版读取 `updates-lite.json`，两个版本各自更新，不会互相切换。
